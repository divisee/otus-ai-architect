# Выбор движка инференса для основной модели

## Статус

**Предложено** — **единый движок во всех средах: vLLM**. SGLang — задокументированная
будущая оптимизация (оценивается за роутером, **не** держим параллельно).

> Пересмотрено: ранее рассматривали «SGLang в Prod + vLLM в Dev», но это требует
> поддерживать **два стека** с разной конфигурацией и **разной наблюдаемостью**,
> а Stage по PRD (§4) должен «имитировать Prod максимально близко». Поэтому
> выбираем **один движок** для Dev/Stage/Prod.

## Контекст

Модель — **T-pro-it-2.1** (на базе Qwen3-32B); её карточка рекомендует **SGLang**.
Профиль нагрузки специфичен:
- **RAG**: у запросов общий префикс (system-prompt + инструкции + повторяющиеся
  фрагменты БЗ) → высокая доля **prefix reuse**.
- **Агентный roadmap (FR-18)**: tool-calling и **структурированный вывод (JSON)**.
- Низкий RPS (5–10), latency p95 ≤ 15 с, 1 GPU (ADR-0003).

Для таких профилей ключевые свойства движка — кэш общих префиксов и эффективный
constrained-decoding для JSON/tool-calls, а не только пиковый throughput.

## Рассматриваемые варианты

| Движок | Сильные стороны | Слабые стороны | Под наш профиль |
|---|---|---|---|
| **SGLang** | **RadixAttention** (точный prefix-reuse → до ~6× на RAG/multi-turn); **xGrammar** для JSON/tool-calls (~3–5× throughput, ~99.8% валидность); ниже p95 TTFT под нагрузкой; рекомендован карточкой T-pro | NVIDIA-центричность; нужен прогрев кэша; экосистема младше vLLM | **Лучший**: RAG-префиксы + агентный JSON |
| **vLLM** | PagedAttention, огромная экосистема, простая эксплуатация, OpenAI-API, **лучший TTFT при c=1**; AWQ/GPTQ+Marlin, FP8 | На RAG/structured-output уступает SGLang | Отличный **fallback/Dev** |
| **TGI** | Интеграция с HF, простой деплой, гибкая квантизация (INT4) | Ниже throughput; 1 LoRA на сервер | Только если деплой на HF Endpoints |
| **TensorRT-LLM** | Максимальная плотность на H100 (FP8) | **Компиляция движка 25–40 мин на версию**, сложность, нужна экспертиза | Избыточно для 5–10 RPS |

## Решение

**Единый движок для Dev/Stage/Prod — vLLM.** Причины:
1. **Операционная простота и зрелая наблюдаемость**: один стек, одни метрики
   (Prometheus/Grafana), один набор конфигов — Dev = Stage = Prod (§4 PRD).
   Это снимает риск «работало в Dev — сломалось в Prod».
2. При нашей **низкой конкурентности (5–10 RPS)** vLLM даёт **лучший TTFT**
   (преимущество SGLang по throughput раскрывается при высокой конкурентности,
   которой у нас нет).
3. У vLLM есть **automatic prefix caching** — он покрывает основную часть выгоды
   от общих RAG-префиксов, и **structured outputs** для tool-calls.
4. Широчайшая экосистема, поддержка нашей модели (Qwen3-base), AWQ/GPTQ+Marlin, FP8.

**SGLang — не держим параллельно.** Его сильные стороны (RadixAttention,
xGrammar) ценны для high-concurrency RAG и агентного JSON; оставляем как
**будущую оптимизацию**: если нагрузка/агентность вырастут и бенчмарк на нашем
трафике покажет выигрыш — мигрируем **полностью** (Dev→Stage→Prod) за
OpenAI-совместимым роутером (ADR-0002), а не запускаем второй движок.

**TGI** — не выбираем (нет деплоя на HF Endpoints). **TensorRT-LLM** — отклонён:
выигрыш не оправдывает сложность компиляции при 5–10 RPS.

В любом случае: квантизация **AWQ/GPTQ INT4 (+Marlin)** или **FP8** (на H100),
**continuous batching**, **FP8 KV-cache**, **automatic prefix caching**.

## Последствия

### Плюсы
- **Один движок** во всех средах → единая конфигурация и наблюдаемость, меньше
  операционных рисков и нагрузки на команду.
- Лучший TTFT при нашей низкой конкурентности → запас по SLA (p95 ≤ 15 с).
- Зрелая экосистема и метрики; automatic prefix caching покрывает RAG-префиксы.
- Роутер (ADR-0002) оставляет путь к полной миграции на SGLang, если понадобится.

### Минусы (trade-offs)
- На high-concurrency RAG и агентном структурированном выводе vLLM уступает
  SGLang (RadixAttention/xGrammar) — осознанно жертвуем пиковой эффективностью
  ради операционной простоты, пока нагрузка низкая.
- При сильном росте агентности/нагрузки может потребоваться миграция на SGLang
  (разовый проект), но **без параллельной эксплуатации двух движков**.

### Проверка
На целевом GPU (ADR-0003) подтвердить, что **vLLM** на нашем трафике (RAG-префиксы +
JSON tool-calls) держит p95 ≤ 15 с при 10 RPS. Параллельно — разовый бенчмарк
SGLang как ориентир: мигрируем целиком только при существенном выигрыше под
выросшую нагрузку.
