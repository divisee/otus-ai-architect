## Маршрут и цели (Раздел I)

| # | Умение | Зачем |

> **Тезис раздела:** для AI эксперимент должен быть воспроизводим **вместе с инфраструктурой**, а пайплайн доставки — проверять не только код, но и качество модели.

---

## Зачем IaC AI-архитектору

**Infrastructure as Code (IaC)** — описание инфраструктуры декларативными конфигами в Git, а не «кликами в консоли».

**Проблемы без IaC:**

1. Инфраструктура создаётся вручную — воспроизвести сложно.
2. Нет версионирования: непонятно, что и когда изменилось.
3. Для AI это критично: эксперимент должен быть воспроизводим вместе с окружением (GPU-ноды, бакеты, сети, реестры).

**Что даёт IaC:**

1. Инфраструктура в Git — как код, с ревью и историей.
2. Один конфиг разворачивает окружения: **dev / staging / prod**.
3. Откат изменений прост — через Git + повторный `apply`.

> **Аналогия.** Без IaC — собирать стенд «по памяти»; с IaC — рецепт в репозитории: любой может поднять такой же стенд и понять, чем prod отличается от staging.

## Terraform: концепции и цикл работы

**Terraform** (HashiCorp, Go) — декларативный IaC-инструмент: описываете желаемое состояние ресурсов, Terraform приводит облако к нему. Работает с облачными провайдерами ([terraform.io](https://www.terraform.io)).

| Концепция | Суть | Пример |
|-----------|------|--------|
| **Provider** | Драйвер к облаку / API | Для Yandex Cloud: `yandex-cloud/yandex` |
| **Resource** | Объект инфраструктуры | Сеть, кластер K8s, бакет Object Storage |
| **State** | Файл состояния: что уже создано и чем Terraform управляет | `terraform.tfstate` (обычно remote state) |

**Цикл работы:**

```bash
terraform init     # скачать провайдер
terraform plan     # показать, что изменится (diff)
terraform apply    # применить изменения
terraform destroy  # удалить управляемые ресурсы
```

> **Тезис блока:** `plan` перед `apply` — обязательная привычка: смотрите diff, потом применяете. State — источник правды о том, чем Terraform уже владеет.

## Типичная инфраструктура AI в облаке

| Компонент | Зачем в AI-системе |
|-----------|-------------------|
| **VPC + подсети** | Изоляция окружений, безопасность, зоны доступности |
| **Managed Kubernetes** | Запуск контейнеров: inference, training, preprocessing |
| **Object Storage** | Датасеты, чекпоинты, артефакты моделей |
| **Container Registry** | Версионирование Docker-образов сервисов |
| **Managed PostgreSQL** | Метаданные экспериментов, feature store |
| **IAM + сервисные аккаунты** | Разграничение прав между компонентами |

> **Тезис блока:** AI-инфраструктура — не «только GPU». Нужны сеть, оркестрация, хранилище артефактов, реестр образов, БД метаданных и строгий IAM.

## CI/CD для AI vs классический Software

**CI/CD** — непрерывная интеграция и непрерывная доставка/развёртывание: ускорение жизненного цикла разработки за счёт автоматизации сборки, тестов и выката.

| Аспект | Software | AI |
|--------|----------|-----|
| **Артефакт** | Docker-образ | Образ + **веса модели** + конфиг |
| **Тестирование** | unit / integration | + **качество модели**, метрики |
| **Откат** | Предыдущий образ | Предыдущий образ + **предыдущая версия модели** |
| **Триггер** | Push в репозиторий | Push + **новые данные**, **дрейф модели** |

> **Главная сложность AI:** модель может «сломаться» не из-за бага в коде, а из-за **изменения данных или гиперпараметров**.

## Пайплайн CI/CD (пример GitLab) и Quality Gates

Пример этапов пайплайна для AI-сервиса:

| Этап | Что происходит |
|------|----------------|
| **START** | Push в GitLab — старт пайплайна |
| **BUILD** | Сборка образа → push в Container Registry |
| **TEST** | Unit-тесты, интеграционные тесты API |
| **SECURITY** | SAST, сканирование контейнеров |
| **VALIDATE** | Загрузка весов из S3 → прогон на validation dataset → проверка метрик |
| **DEPLOY** | Обновление Helm-чарта в Kubernetes |
| **MONITORING** | Реальный запрос к inference → проверка ответа и latency |

**Quality Gates** — пороги, при нарушении которых пайплайн останавливается:

| Gate | Инструменты | Критерий остановки |
|------|-------------|-------------------|
| Линтеры кода | ruff, black, isort | Любая ошибка |
| Линтеры IaC/K8s | `tf validate`, tflint, helm lint | Любая ошибка |
| Unit-тесты | pytest | Coverage < порога |
| Безопасность | semgrep, trivy | Критические уязвимости, секреты |
| Качество модели | custom script | Метрика < порога |
| Smoke-тесты | curl | Плохие статусы / latency |

> **Тезис блока:** в AI CI/CD есть отдельный этап **VALIDATE** и gate по метрикам модели — без них в prod уедет «зелёный» код с плохой моделью.

## MLOps vs DevOps

| | **DevOps** | **MLOps** |
|--|------------|-----------|
| Фокус | Разработка + эксплуатация ПО | + **данные** и **качество модели** |
| Артефакт | Работающий сервис (работает / не работает) | Сервис может работать технически, но **деградировать** из-за drift |
| Практики | CI/CD, IaC, мониторинг сервисов | + версионирование датасетов, feature store, метрики модели, переобучение |

> **Тезис блока:** MLOps **не заменяет** DevOps — это соседняя дисциплина. Без governance, мониторинга, feature store и CI/CD стек неполный.

---

## MLOps-конвейер и стек инструментов

**MLOps-конвейер** — автоматизированная цепочка без ручного вмешательства:

```
сбор данных → обучение → валидация → деплой → мониторинг
```

**Три инструмента стека:**

| Инструмент | Роль | Суть |
|------------|------|------|
| **Apache Airflow** | Оркестрация | Порядок задач, расписание, retry. Python DAG, UI. **Не знает** про ML-артефакты |
| **MLflow** | «Память» системы | Логи параметров/метрик/артефактов; Model Registry: Staging → Production; lineage |
| **Kubeflow** | Масштабирование | ML-платформа на K8s, GPU/TPU; сложная настройка, высокий порог входа |

**Airflow:** плюсы — гибкость DAG, экосистема операторов, интеграции. Минусы — нет нативной поддержки ML-артефактов, нужен DevOps, не заточен под эксперименты.

**MLflow:** без него никто не знает, какая модель на каких данных и с какими параметрами; с ним — полная lineage каждой модели.

**Kubeflow:** нативная поддержка ML-экспериментов и масштабирование, но тесная привязка к K8s.

> **Минимальный MLOps-стек:** real-time мониторинг модели + контроль версий модели/данных + политики обновления версий.

## Переобучение и выбор деплоя

**Когда запускать retrain:**

| Тип триггера | Примеры |
|--------------|---------|
| **По времени** | Еженедельно (стабильные данные); ежедневно (быстро меняющаяся среда); по N новых сэмплов |
| **По качеству** | Падение метрик ниже порога; data drift > threshold; жалобы пользователей / аномалии |

**Стратегии деплоя модели (кратко):**

| Стратегия | Идея | Плюс / минус |
|-----------|------|--------------|
| **Blue-Green** | Две полные среды (v1 и v2), мгновенный switch трафика | Быстрый откат; дорого по ресурсам |
| **Canary** | Постепенно 5% → 25% → 100%, контроль метрик на каждом шаге | Меньше риск, дольше по времени |

## Model Drift: типы, обнаружение, реакция

**Model Drift** — деградация качества модели в проде, потому что реальные данные перестают соответствовать обучающим.

| Тип | Что меняется | Пример |
|-----|--------------|--------|
| **Data Drift** | Распределение входов **[X]** | Другой портрет пользователя, другой регион, выбросы/пропуски |
| **Concept Drift** | Связь **[X → Y]** | Поведение пользователей изменилось из-за внешних событий; модель на «старой реальности» |

**Инструменты обнаружения:**

| Слой | Что | Примеры |
|------|-----|---------|
| Статистика | Сравнение train vs prod | KS-test, **PSI**, Chi-square |
| Отчёты по дрейфу | Готовые отчёты | **Evidently AI** |
| Real-time | Latency, prediction distribution, feature stats | **Prometheus + Grafana** |
| Реакция | Алерт + автозапуск | PagerDuty / почта + **retrain DAG в Airflow** |

**Кейс (рекомендации после праздников):** PSI > 0.2 → Evidently JSON-отчёт → Grafana-алерт → Airflow retrain на данных 30 дней → валидация → деплой на часть пользователей.

> **Тезис блока:** риски model drift нужно закладывать **на этапе проектирования**, а не «когда уже упало в проде».

## Практика: MLOps-пайплайн для RAG

**RAG (Retrieval Augmented Generation)** — ответ LLM строится на релевантных документах из векторной базы.

**Задача:** документы еженедельно обновляются в S3 → нужно автоматически пересчитать эмбеддинги и обновить векторную БД (Chroma / FAISS / Qdrant).

### Архитектура пайплайна

**Trigger:** новый документ в S3 **или** cron.

1. Airflow DAG → загрузчик документов  
2. Chunking + Embedding (OpenAI / HuggingFace)  
3. Upsert в Chroma / Qdrant / FAISS  
4. Smoke-test — поиск по 5 тестовым запросам  
5. Версионирование снэпшота векторной базы  

**Мониторинг:** retrieval latency, hit rate, user feedback. Расширенно — DeepEval: precision, recall, F1, contextual precision/recall.

### Три группы компонентов

**1. Источники данных**

| Компонент | Назначение |
|-----------|------------|
| Document Store (S3) | Исходные документы |
| Crawler / Loader | Сбор новых файлов (LangChain DocumentLoader) |
| Preprocessor | Очистка, chunks **512–1024** токена |
| Metadata tagger | source, date, version на чанк |
| Change detector | Новые / изменённые / удалённые документы |

**2. Эмбеддинги и векторная база**

| Компонент | Назначение |
|-----------|------------|
| Embedding-модель | `text-embedding-3-small` или `all-MiniLM` |
| Batch inference | Пачки чанков — экономия API и latency |
| Vector DB | Qdrant / Weaviate с upsert |
| Версионирование | Каждый rebuild — снэпшот с датой |
| Smoke test | 5–10 запросов **до** переключения на новую версию |

**3. Мониторинг и автотриггеры**

| Метрика / действие | Смысл |
|--------------------|-------|
| Retrieval latency (avg, P99) | Скорость поиска |
| Hit rate | Доля запросов с similarity > threshold (напр. 0.75) |
| User feedback | Лайк / дизлайк |
| Auto-trigger | Hit rate < 0.6 **или** N+ новых документов → DAG |
| Rollback | Падение метрик → откат к предыдущей версии базы |

> **Тезис блока:** для RAG «модель» в широком смысле — ещё и **версия индексной базы**. Её тоже версионируют, тестируют smoke-тестами и откатывают.

## ML CI/CD: код + данные + модель

В классическом CI/CD главный артефакт — **код**. В ML — три артефакта: **код + данные + модель**.

### Данные

| Направление | Что делать | Инструменты |
|-------------|------------|-------------|
| **Versioning & Lineage** | Snapshots/hashes датасетов; lineage raw → features → train/val/test | DVC, lakeFS, Delta/Iceberg/Hudi, MLflow metadata |
| **Data Quality & Contracts** | Schema, constraints, nulls/ranges; contracts producer ↔ consumer; training-serving skew | Great Expectations, Pandera, dbt tests, Soda |
| **Drift & Monitoring** | Data / concept drift сигналы | Evidently, WhyLabs, Arize + Prometheus/Grafana |

### Модель

| Направление | Что делать |
|-------------|------------|
| **Repo & Structure** | Monorepo vs multi-repo (train / serve / features); packaging libs + pipelines + serving |
| **Build & Dependencies** | Pinned deps + lockfiles; hermetic builds; контейнеры как артефакты (train/serve images) |
| **Tests & Quality Gates** | Unit + integration **и** metric thresholds + regression vs baseline; slicing, fairness, robustness, calibration |
| **CI hygiene** | Code review, pre-commit, conventions |

> **Тезисы блока:**  
> 1) артефакты = код + данные + модель;  
> 2) тесты в ML — не только pass/fail кода;  
> 3) основа — **воспроизводимость и трассируемость**.

## Стратегии релиза: Blue-Green, Rolling, Canary, Shadow

### Blue-Green и Rolling

| Стратегия | Как работает | Rollback | Когда хорошо |
|-----------|--------------|----------|--------------|
| **Blue/Green** | Два окружения, switch трафика «рубильником» | Очень быстрый | Предсказуемое поведение сервиса, нужна мгновенная смена версии |
| **Rolling** | Постепенная замена инстансов в **одном** окружении | Зависит от стратегии | Экономия ресурсов vs Blue-Green |

### Canary

- Новая версия получает **X%** трафика; доля растёт по шагам (например 5% → 25% → 100%).
- **Метрики-гейты** на каждом шаге: SLO (latency/errors) + KPI / ML-метрики.
- Rollback: вернуть **0%** на canary за минуты.
- Реализация: Ingress / Service Mesh / traffic router.

**Пример: NGINX Ingress (5% на canary):**

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"
```

**Пример: Istio VirtualService (95% stable / 5% canary):**

```yaml
http:
- route:
  - destination:
      host: my-model-stable-svc
    weight: 95
  - destination:
      host: my-model-canary-svc
    weight: 5
```

### Shadow / Dark launch

| | |
|--|--|
| Идея | Запросы **дублируются** на новую версию; пользователю отвечает **стабильная** |
| Проверяем | Ошибки, latency, совместимость, распределение предсказаний |
| Риск для пользователей | **Нулевой** |
| Ограничение | Не измеряет бизнес-эффект напрямую |

### Сравнение (ориентиры)

| Стратегия | Сигнал | Риск для пользователей | Стоимость / сложность |
|-----------|--------|------------------------|----------------------|
| **Shadow** | Технический (ошибки, latency, распределение) | Нет | Дублирование нагрузки |
| **Canary** | SLO + KPI/ML на реальном % трафика | Низкий, контролируемый | Нужен traffic split + гейты |
| **Rolling** | Постепенная замена инстансов | Средний | Проще по ресурсам |
| **Blue/Green** | Полный switch | Низкий при быстром rollback | 2× окружения |

> **Безопасный стандарт для моделей:**  
> **Shadow** (техника) → **Canary** (контролируемый риск) → **A/B** (доказательство эффекта) → **promote / rollback**.

---

## Model routing, A/B и Feature flags

**Model routing** — управление, какая модель обслуживает какой трафик:

| Паттерн | Суть |
|---------|------|
| **A/B test** | Сравнение двух моделей по KPI (через canary / flags) |
| **Champion / Challenger** | Stable vs candidate в Model Registry + промоут |
| **Цепочка** | Shadow → Canary → A/B → Promote |
| **Bandits / online learning** | Динамическое перераспределение трафика (если применимо) |

### Feature flags: Deploy ≠ Release

**Feature flag** — условие в коде, которое включает/выключает поведение **без нового деплоя**. Код уже в production; «релиз» — включение для пользователей.

| Применение | Пример |
|------------|--------|
| Progressive rollout | 1% → 5% → 25% → 100% |
| Сегментация | geo / tenant / cohort / internal users |
| Kill switch | Быстро выключить при деградации SLO/KPI |
| Основа A/B | Контрольная и тестовая группы |

**Простой custom-бакетинг:**

```python
def choose_model(user_id: str) -> str:
    bucket = hash(user_id) % 100
    return "model_v2" if bucket < 10 else "model_v1"  # 10% на v2

def predict(request, user_id):
    model_name = choose_model(user_id)
    try:
        return models[model_name].predict(request)
    except TimeoutError:
        return models["model_v1"].predict(request)  # fail-safe
```

Платформенный вариант — **Unleash**: percentage rollout + сегментация по `userId` / properties (tenant, country).

> **Тезисы блока:**  
> 1) **Deploy ≠ Release**;  
> 2) стратегии отличаются по сигналу / риску / стоимости;  
> 3) решение о выкатке опирается на **три вещи: SLO, бизнес-KPI, ML-метрики**;  
> 4) качественный релиз невозможен без наблюдаемости и разметки эксперимента.

## Паттерны деплоя инференса: Batch / Async / Sync

Три сценария обслуживания:

| Паттерн | Характер | Типичная задержка |
|---------|----------|-------------------|
| **Batch** | Пакетный пересчёт по расписанию | Часы–дни |
| **Async** | Запрос в очередь, ответ позже / callback | Секунды–минуты |
| **Sync** | Запрос–ответ online | Миллисекунды–секунды |

**Как выбрать:**

1. Требуемая задержка: ms / sec–min / hours–days  
2. Критичность для UX: блокирует пользователя или нет  
3. Нагрузка и стоимость: QPS, пики, GPU/CPU  
4. Свежесть результата: нужен сейчас или достаточно раз в день/месяц  
5. Надёжность: retries, backpressure, деградация  
6. Где живут фичи: online store/cache vs DWH snapshot  

**Кейсы из занятия:**

| Кейс | Задача | Логичный паттерн |
|------|--------|------------------|
| **A. Risk pricing** | Ночной пересчёт риск-скора по всем полисам → витрина | **Batch** |
| **B. LLM support-чат** | Draft reply оператору по истории и базе знаний | **Sync** (или sync + async для тяжёлых шагов) |
| **C. IoT-аномалии** | Телеметрия → тревога / остановка линии | **Sync** (или near-real-time stream), жёсткие SLO |

> **Тезис блока:** паттерн деплоя выбирается **требованиями бизнеса**, а не типом модели.

## Итоги трёх занятий

1. **IaC (Terraform)** даёт воспроизводимую AI-инфраструктуру в Git; типичный стек — VPC, Managed K8s, Object Storage, CR, PostgreSQL, IAM.  
2. **CI/CD для AI** расширяет классический: артефакт = образ + веса + конфиг; триггеры включают данные и drift; нужны VALIDATE и quality gates по метрикам.  
3. **MLOps** добавляет к DevOps данные и качество модели; стек — Airflow (оркестрация) + MLflow (память) + Kubeflow (масштаб на K8s).  
4. **Model drift** (data / concept) проектируется заранее: Evidently + Prometheus/Grafana + авто-retrain.  
5. Для **RAG** версионируют и откатывают не только модель, но и **снэпшот векторной базы**.  
6. **Deploy ≠ Release**; безопасная цепочка: Shadow → Canary → A/B → promote/rollback.  
7. Feature flags / model routing дают управляемость; решение о выкатке — по SLO + KPI + ML-метрикам.  
8. Batch / Async / Sync выбирают по latency, UX, стоимости и свежести данных.
