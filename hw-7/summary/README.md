## Зачем это архитектору

LLM — самый дорогой компонент AI-системы в эксплуатации. Одна карта NVIDIA A100 стоит около **200–470 тыс. ₽/мес** в аренду, а большая модель требует нескольких таких карт. Ошибка в сайзинге на «пару GPU» — это сотни тысяч рублей в месяц или, наоборот, падающий под нагрузкой сервис.

Архитектор должен уметь ответить на три вопроса **ещё до закупки железа**:

1. **Влезет ли модель в память?** — считаем VRAM (веса + KV cache + overhead).
2. **Справится ли конфигурация с нагрузкой?** — считаем пропускную способность (токены/с) под целевой RPM.
3. **Как сделать дешевле, не убив качество?** — квантование + правильный движок инференса (vLLM: батчинг, PagedAttention, FlashAttention).

Этот конспект даёт формулы, разбирает механику «под капотом» и показывает расчёты на примере **Llama-3-70B**.

> **Аналогия.** Сайзинг LLM похож на подбор автопарка под доставку: сначала смотрим, влезает ли груз в кузов (**VRAM**), потом — сколько машин нужно, чтобы развозить N заказов в час (**throughput/RPM**), и наконец — как возить дешевле: меньше расход топлива (**квантование**) и не гонять полупустые машины (**батчинг**).

## Расчёт сайзинга VRAM

### Устройство трансформера: откуда берутся параметры

Чтобы понимать, откуда берётся объём модели, нужно знать её строение. Трансформер — это **стопка одинаковых блоков (слоёв)**, между которыми «зажаты» эмбеддинги на входе и голова языкового моделирования на выходе. Каждый слой состоит из двух подблоков: **внимание (Attention)** и **полносвязная сеть (FFN)**.

Введём обозначения: `d` — размерность скрытого состояния (hidden size), `L` — число слоёв, `V` — размер словаря, `d_ff` — внутренняя размерность FFN (обычно `d_ff ≈ 4·d`).

| Блок | Что делает | Параметров |
|------|-----------|:---:|
| **Эмбеддинги токенов** | превращает id токена в вектор длины `d` | `V · d` |
| **Позиционные эмбеддинги** | кодируют позицию токена (в новых моделях — RoPE, без весов) | `≈ ctx · d` |
| **Attention (Q, K, V, O)** | 4 матрицы проекций `d × d` на слой | `4 · d²` |
| **FFN** | 2 матрицы `d × d_ff` (расширение и сжатие) | `2 · d · d_ff = 8 · d²` |
| **LayerNorm** | 2 нормализации на слой, по `~2d` параметров | `≈ 4 · d` (пренебрежимо) |

**Разбор на примере GPT-3** (`d = 12288`, `L = 96`, `V ≈ 50257`, `ctx = 2048`):

| Блок | Формула | Значение |
|------|---------|:---:|
| Матрица эмбеддера | `50257 × 12288` | **617M** |
| Позиционные эмбеддинги | `2048 × 12288` | **25M** |
| Головы внимания (Q,K,V,O) на слой | `4 × 12288²` | **605M** |
| FFN на слой (`d_ff = 4d`) | `2 × 12288 × 49152` | **1208M** |
| Нормализации на слой | `4 × 12288` | **49K** |

**Итого:** `617M + 25M + 96 × (605M + 1208M + 49K) ≈ 175B` параметров.

> **Тезис блока:** основной вклад дают **FFN (≈ 2/3)** и **внимание (≈ 1/3)**, повторённые `L` раз. Эмбеддинги весомы только у «маленьких» моделей с большим словарём. Параметры растут **линейно по числу слоёв** и **квадратично по `d`**.

### Правило «12 · d² · L» и пример подсчёта

Сложим параметры одного слоя: `4·d²` (внимание) + `8·d²` (FFN) = **`12·d²`**. Отсюда быстрая прикидка размера модели (без эмбеддингов):

```
N_параметров ≈ 12 · d² · L
```

**Проверка на GPT-3:** `12 × 12288² × 96 = 12 × 150.99M × 96 ≈ 174B` ✅ (совпадает с 175B).

**Осторожно с современными моделями.** Формула `12·d²·L` — для «классического» трансформера. В **Llama-3** есть два отличия:

- **SwiGLU FFN** — не 2, а **3 матрицы** и `d_ff ≈ 3.5·d` вместо `4·d` → FFN тяжелее.
- **GQA** — у K и V меньше «голов», чем у Q → блок внимания **легче** по параметрам и (важно!) сильно легче по KV cache.

Поэтому для точного числа всегда смотрят `config.json` модели на Hugging Face, а формулу используют для быстрой оценки «на салфетке».

> **Практика:** зная только `d` и `L`, вы за 10 секунд прикидываете масштаб модели. Например, `d=4096, L=32` → `12 × 4096² × 32 ≈ 6.4B` — это примерно Llama-2-7B.

### Формула VRAM

Базовая формула объёма видеопамяти для инференса:

```
VRAM = (Количество параметров × Вес одного параметра) + KV cache + Overhead
```

Три слагаемых:

1. **Веса модели** = `Параметры × байт_на_параметр` — постоянная величина, зависит только от модели и точности.
2. **KV cache** — кэш внимания; растёт с длиной контекста и числом одновременных запросов (см. ниже). Переменная величина, зависит от нагрузки.
3. **Overhead** — CUDA-контекст (~1–2 GB на процесс), активации, временные буферы, фрагментация аллокатора. На практике закладывают **+10…20 %** к весам.

> **Тезис блока:** память ≠ только веса. Веса — это «пол», ниже которого не опуститься. А **KV cache** под нагрузкой с длинным контекстом может занимать десятки и сотни ГБ и часто становится **главным ограничителем** числа одновременных пользователей.

### Веса модели: FP32 / FP16 / INT8 / INT4 + пример

«Вес» одного параметра = число байт для хранения одного числа. Чем ниже точность, тем меньше байт:

| Точность | Бит | Байт на параметр | Веса для 70B | Веса для 7B |
|----------|:---:|:---:|:---:|:---:|
| FP32 | 32 | 4 | 280 GB | 28 GB |
| FP16 / BF16 | 16 | 2 | 140 GB | 14 GB |
| INT8 | 8 | 1 | 70 GB | 7 GB |
| INT4 | 4 | 0.5 | 35 GB | 3.5 GB |

**Пример (Llama-3-70B).** Веса в FP16: `70 · 10⁹ × 2 байта = 140 · 10⁹ байт = 140 GB`. В INT4: `70 · 10⁹ × 0.5 = 35 GB`.

Что это значит на практике для карт с разной VRAM:

- **FP16 (140 GB)** не влезает ни на одну карту (у топовой A100/H100 — 80 GB) → нужен **tensor parallelism** на несколько GPU.
- **INT4 (35 GB)** спокойно помещается на **одну A100-80GB**, оставляя ~40 GB под KV cache и overhead. Это и есть «магия» квантования: смена класса железа.

> ⚠️ **Про «GB» и «GiB».** Здесь и в ДЗ мы считаем в десятичных `GB` (1 GB = 10⁹ байт) — так удобнее сверяться с прайсами облаков. Утилиты (nvidia-smi, калькуляторы) часто показывают **GiB** (2³⁰ = 1.074 · 10⁹). Разница ~7 %: 140 GB ≈ 130.4 GiB. Для сайзинга это в пределах закладываемого overhead, но помнить полезно.

### KV cache: вывод формулы и пример

**Зачем он нужен.** Модель генерирует текст **по одному токену за шаг** (авторегрессия). На каждом шаге внимание считает, как новый токен «смотрит» на все предыдущие — для этого нужны их векторы **K (ключи)** и **V (значения)**. Если каждый раз пересчитывать K/V для всей истории, сложность растёт квадратично. Решение — **закэшировать** уже посчитанные K и V; пересчитывать приходится только `Q` нового токена.

**Объём кэша на один токен:**

```
KV_на_токен = 2 × n_layers × n_kv_heads × head_dim × байт_на_элемент
```

- `2` — храним отдельно K и V;
- `n_layers` — на каждом слое свой кэш;
- `n_kv_heads × head_dim` — размерность одного вектора K (и V);
- `байт_на_элемент` — обычно 2 (KV держат в FP16), можно квантовать до INT8/FP8.

**Полный кэш:**

```
KV = KV_на_токен × длина_контекста × число_одновременных_запросов
```

**Пример (Llama-3-70B, FP16 KV):** `n_layers=80`, `n_kv_heads=8` (GQA!), `head_dim=128`.

```
KV_на_токен = 2 × 80 × 8 × 128 × 2 байта = 327 680 байт ≈ 0.3125 MB
```

- На один запрос с контекстом **8192** токенов: `0.3125 MB × 8192 ≈ 2.5 GB`.
- На **100 одновременных** запросов по 8192 токенов: `100 × 2.5 GB = 250 GB` (!) — больше, чем сами веса.

**Эффект GQA.** Если бы Llama-3-70B использовала классическое **MHA** (64 KV-головы вместо 8), кэш был бы в 8 раз больше:

```
MHA: 2 × 80 × 64 × 128 × 2 = 2 621 440 байт ≈ 2.5 MB/токен  (в 8× больше!)
```

Именно поэтому современные большие модели используют **GQA** — иначе длинный контекст «съедал» бы всю память.

> **Тезис блока:** KV cache линеен по длине контекста и по числу параллельных запросов. Он определяет, **сколько пользователей влезет** в память после загрузки весов. Рычаги его уменьшения: **GQA** (архитектура), **квантование KV** (FP16→FP8/INT8), **PagedAttention** (борьба с фрагментацией — см. ниже).

### Память под обучение (fine-tuning)

Вторая цель занятия — оптимизация **обучения**. Здесь память нужна не только под веса: при полном дообучении (full fine-tune) с оптимизатором **Adam** на каждый параметр хранятся ещё и градиент и два состояния оптимизатора (моменты `m` и `v`).

| Что храним при full fine-tune (mixed precision) | Байт на параметр |
|--------------------------------------------------|:---:|
| Веса (FP16) | 2 |
| Градиенты (FP16) | 2 |
| Master-копия весов (FP32) | 4 |
| Момент `m` Adam (FP32) | 4 |
| Момент `v` Adam (FP32) | 4 |
| **Итого** | **≈ 16** |

**Пример.** Full fine-tune Llama-3-70B: `70 · 10⁹ × 16 ≈ 1120 GB` — плюс активации. Это **14+ карт A100-80GB** только под состояние — дорого и сложно.

**Как экономят память при обучении:**

| Приём | Суть | Эффект |
|-------|------|--------|
| **LoRA** | Обучаем не всю модель, а маленькие «адаптеры» (низкоранговые матрицы), веса заморожены | Обучаемых параметров < 1 % → в разы меньше памяти под оптимизатор |
| **QLoRA** | База модели квантована в **4 бита**, поверх — LoRA-адаптеры | 70B дообучается на **1–2 картах** вместо 14+ |
| **Gradient checkpointing** | Не храним все активации, а пересчитываем их при backward | Меньше памяти под активации ценой ~30 % времени |
| **ZeRO / FSDP** | Шардирование весов, градиентов и состояний оптимизатора между GPU | Линейная экономия по числу карт |
| **Mixed precision (BF16)** | Считаем в 16 бит, master-копия в FP32 | ~2× память и скорость на forward/backward |

> **Тезис блока:** обучение прожорливее инференса в **~8–10 раз** (оптимизатор + градиенты + активации). **QLoRA** — стандартный способ дообучить большую модель на скромном железе.

## Квантование

### Что это и зачем

**Квантование (quantization)** — метод сжатия весов и активаций LLM за счёт **уменьшения точности их представления** (например, FP16 → INT4). Позволяет:

- **уменьшить требования к памяти** (в т.ч. VRAM);
- **ускорить инференс** — большинство операций инференса *memory-bound*, а меньшие веса быстрее грузятся из памяти (меньше байт качаем из HBM).

**Побочный эффект:** снижение точности предсказаний модели.

> **Интуиция.** Веса — это числа вроде `0.4732`. Хранить их в 16 битах точно, но дорого. Квантование говорит: «давай разобьём весь диапазон значений на 16 (INT4) или 256 (INT8) уровней и будем хранить только номер уровня». Номер уровня занимает 4 или 8 бит вместо 16. При чтении номер «разворачивается» обратно в приблизительное число.

### Как это работает: scale и zero-point

Квантование отображает диапазон вещественных чисел `[min, max]` в целые `[0, 2ⁿ−1]` (для INT8: `[0, 255]` или `[−128, 127]`). Два ключевых коэффициента:

- **scale (`s`)** — «цена деления», сколько вещественных единиц в одном шаге кванта: `s = (max − min) / (q_max − q_min)`.
- **zero-point (`z`)** — какому целому соответствует вещественный ноль.

Формулы:

```
квантование:      q = round(x / s) + z
деквантование:    x' ≈ (q − z) × s
ошибка:           |x − x'|  (тем меньше, чем больше бит)
```

**Числовой пример (INT8, асимметричный).** Пусть веса лежат в диапазоне `[−0.8, 1.2]`, целевой диапазон `[0, 255]`.

- `s = (1.2 − (−0.8)) / (255 − 0) = 2.0 / 255 ≈ 0.00784`
- `z = round(0 − min/s) = round(0.8 / 0.00784) ≈ 102`
- Квантуем `x = 0.5`: `q = round(0.5 / 0.00784) + 102 = 64 + 102 = 166`
- Деквантуем обратно: `x' = (166 − 102) × 0.00784 = 0.502` → ошибка всего `0.002`.

Число `0.5` теперь хранится как **один байт `166`** вместо двух — вдвое компактнее, а потеря точности в третьем знаке.

### Симметричное vs асимметричное квантование

- **Симметричное** — диапазон симметричен относительно нуля, поэтому `z = 0`, а `s = max(|x|) / q_max`. Проще и быстрее (одно умножение, без вычитания zero-point). Хорошо для **весов**, которые обычно распределены симметрично вокруг нуля.
- **Асимметричное** — вводится `z ≠ 0`, диапазон может быть несимметричным. Точнее для «сдвинутых» распределений — например, **активаций после ReLU** (все значения ≥ 0).

**Тот же `x = 0.5` симметрично** (диапазон `[−1.2, 1.2]`): `s = 1.2/127 ≈ 0.00945`, `q = round(0.5/0.00945) = 53`, `x' = 53 × 0.00945 = 0.501`.

| | Симметричное | Асимметричное |
|--|--------------|---------------|
| zero-point | `z = 0` | `z ≠ 0` |
| Скорость | быстрее | чуть медленнее |
| Где применяют | веса | активации (особенно после ReLU) |

### Гранулярность: per-tensor / per-channel / per-group

Насколько «крупно» мы подбираем `s` и `z` — важный компромисс между качеством и накладными расходами:

| Гранулярность | Один `(s, z)` на… | Качество | Оверхед |
|---------------|-------------------|:---:|:---:|
| **Per-tensor** | всю матрицу целиком | ниже | минимум |
| **Per-channel** | каждый столбец/строку | выше | средний |
| **Per-group** | блок из N весов (обычно **group size = 128**) | самое высокое при 4 битах | больше метаданных |

Один «выброс» (очень большой вес) при per-tensor растягивает диапазон и грубит квантование всех остальных весов. Поэтому 4-битные методы (**GPTQ/AWQ**) почти всегда используют **per-group** с размером группы 32/64/128.

### Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| Значительно снижает требования к памяти, в т.ч. VRAM | Снижение качества предсказаний, особенно при агрессивной квантизации |
| Ускоряет memory-bound операции → быстрее инференс (меньше весов, смещений, активаций) | Меньше гибкости в инструментах инференса |
| Позволяет уйти на более дешёвые/маленькие GPU | Потенциальные проблемы совместимости и стабильности |

> **Тезис блока:** квантование = обмен небольшой части качества на кратное снижение памяти и стоимости. INT4 обычно уменьшает память под веса **в 4 раза** относительно FP16.

### Разрядность чисел

Чем меньше бит на число, тем меньше памяти и выше скорость, но тем грубее представление и выше риск потери качества.

| Формат | Бит | Уровней значений | Где применяют |
|--------|:---:|:---:|---------------|
| **FP32** | 32 | ~4 млрд | обучение (master-веса), эталон точности |
| **FP16 / BF16** | 16 | ~65 тыс. | стандарт для инференса «как есть»; BF16 шире по диапазону |
| **FP8** (E4M3/E5M2) | 8 | 256 | новые GPU (H100+), KV cache, быстрый инференс |
| **INT8** | 8 | 256 | почти без потери качества, широкая поддержка |
| **INT4** | 4 | 16 | прод-инференс с AWQ/GPTQ, −75 % памяти под веса |
| **2–3 бита** | 2–3 | 4–8 | экстремально, заметная потеря качества |

> **FP16 vs BF16.** Оба по 2 байта. FP16 — больше мантисса (точность), но узкий диапазон (риск переполнения). **BF16** — тот же диапазон, что у FP32 (широкий), но меньше мантисса; устойчивее при обучении, поэтому в LLM чаще берут BF16.

### Подходы к квантованию (PTQ / QAT / динамич. / статич.)

Два независимых деления. **Когда** квантуем:

| Подход | Суть | Плюс / минус |
|--------|------|--------------|
| **PTQ** (Post-Training Quantization) | Квантование **после обучения** готовых весов | Быстро и дёшево (минуты-часы), но чуть больше потеря качества. **Основной путь для LLM** |
| **QAT** (Quantization Aware Training) | Квантование **в процессе обучения** — модель «привыкает» к низкой точности | Лучшее качество, но нужен полный train-цикл (дорого) |

**Что** делаем с активациями:

| Подход | Суть |
|--------|------|
| **Динамическое** | Калибровка активаций **на лету, в процессе инференса**, по реально вычисленным значениям. Точнее, но чуть медленнее |
| **Статическое** | Калибровка (`s` и `z`) выполняется **заранее** на репрезентативном наборе данных (калибровочный датасет). Быстрее в проде |

> **Калибровка** — это прогон через модель небольшого набора типичных данных (сотни примеров), чтобы «увидеть» реальные диапазоны значений и подобрать `s`/`z`. От качества калибровочного датасета зависит итоговая точность.

### Экстремальные подходы (4 бита и меньше): AWQ / GPTQ / GGUF

Наивно порезать веса до 4 бит — качество рухнет. Поэтому придуманы «умные» методы:

| Метод | Идея | Где применяют |
|-------|------|---------------|
| **AWQ** (Activation-aware Weight Quantization) | Замечает: не все веса равны. Выявляет **«сверх-веса» (salient weights)** — те ~1 %, что сильнее всего влияют на активации, — и **защищает их** (масштабирует, не квантует агрессивно). Остальное режет в 4 бита | GPU-инференс, vLLM; отличное качество/скорость |
| **GPTQ** (Generalized PTQ) | Квантует **послойно**, компенсируя ошибку: после квантования одного веса корректирует ещё не квантованные, минимизируя итоговую ошибку слоя. Использует информацию 2-го порядка (**обратная матрица Гессиана**) | GPU-инференс; очень популярен |
| **GGUF** (формат `llama.cpp`) | Не только метод, но и **формат файла**. **Блочное** квантование: на каждый блок весов — свой `scale`. Позволяет грузить в VRAM только часть слоёв (**offload** на CPU/RAM) → запуск на слабом железе | CPU, ноутбуки, локальный запуск, гибрид CPU+GPU |

**Как читать имена GGUF-файлов** (частый вопрос новичков), например `llama-3-70b.Q4_K_M.gguf`:

- `Q4` — 4 бита на вес;
- `_K` — «K-quant» (умное блочное квантование нового поколения);
- `_M` — размер варианта: `S` (small) / `M` (medium) / `L` (large) — компромисс размер/качество.
- Ещё встречаются `Q8_0` (8 бит, максимальное качество), `Q5_K_M`, `Q2_K` (самый маленький и грубый).

> **Тезис блока:** для прод-инференса на GPU берут **AWQ или GPTQ** (высокое качество при 4 битах, скорость). **GGUF** — для CPU/слабого железа, локального запуска и оффлоада.

### Что квантование даёт по качеству

Главный страх — «а не отупеет ли модель?». Ориентиры (по метрике **perplexity** — чем ниже, тем лучше; и по бенчмаркам):

| Точность | Память под веса | Потеря качества (грубо) | Комментарий |
|----------|:---:|:---:|-------------|
| FP16 | 100 % | эталон | база для сравнения |
| INT8 | 50 % | < 1 % | практически незаметно |
| **INT4 (AWQ/GPTQ)** | **25 %** | **~1–3 %** | **лучший баланс для прода** |
| 3 бита | ~19 % | заметная | только если очень жмёт память |
| 2 бита | ~12 % | сильная | почти всегда неприемлемо |

> **Тезис блока:** INT8 — почти без потерь. INT4 с AWQ/GPTQ — **рабочий прод**: −75 % памяти под веса ценой пары процентов качества. Всё, что ниже 4 бит, — на свой страх и риск и только под конкретную задачу.

## Техники оптимизации инференса

### Две фазы инференса: prefill и decode

Генерация ответа LLM состоит из двух очень разных по «характеру» фаз — это важно для понимания всех оптимизаций ниже:

| Фаза | Что происходит | Характер | Узкое место |
|------|----------------|----------|-------------|
| **Prefill** | Обработка всего промпта разом (все входные токены параллельно), заполнение KV cache | Много параллельных вычислений (большие матрицы) → **compute-bound** | Вычислительные ядра GPU |
| **Decode** | Генерация ответа по **одному токену за шаг**, каждый шаг читает все веса и KV cache | Мало вычислений на шаг, много чтения памяти → **memory-bound** | Пропускная способность памяти (HBM) |

**Пример.** Запрос «промпт 500 токенов → ответ 250 токенов»: prefill обрабатывает 500 токенов за один «большой» проход, затем 250 шагов decode генерируют ответ по токену. Основное время пользователь ждёт именно **decode** — и именно его оптимизируют батчингом.

> **Термины метрик:** **TTFT** (Time To First Token) — задержка до первого токена, определяется prefill. **TPOT/ITL** (Time Per Output Token) — время на каждый следующий токен, определяется decode.

### Почему инференс memory-bound: roofline

На шаге **decode** для батча из одного запроса модель умножает вектор на матрицы весов (**GEMV** — matrix×vector). Чтобы посчитать один токен, надо **прочитать из памяти все веса модели** (для 70B в INT4 это 35 GB), а арифметики — мало. Значит, скорость упирается не в вычислительные ядра (TFLOPS), а в **пропускную способность памяти** (GB/s).

**Оценка «потолка».** A100 имеет пропускную способность HBM ~2 ТБ/с. Чтобы сгенерировать 1 токен для INT4-модели (35 GB весов), нужно прочитать эти 35 GB:

```
макс. токенов/с (1 запрос) ≈ 2000 GB/с ÷ 35 GB ≈ 57 токенов/с
```

Вычислительные ядра при этом почти простаивают! **Выход — батчинг:** если обработать сразу 32 запроса, веса читаются из памяти **один раз на весь батч**, а умножение вектора превращается в умножение матриц (**GEMM**) — работа для простаивавших ядер. GPU переходит из memory-bound в compute-bound, и суммарная пропускная способность растёт в разы.

> **Тезис блока:** LLM-инференс на decode **memory-bound**, GPU недозагружен. Все ключевые оптимизации (батчинг, квантование, FlashAttention) бьют именно в память: либо читаем меньше (квантование), либо реже (батчинг), либо ближе (SRAM во FlashAttention).

### Структура памяти GPU

У GPU есть иерархия памяти — как у CPU кэши и RAM:

| Уровень | Объём (A100) | Скорость | Роль |
|---------|:---:|:---:|------|
| **Регистры / SRAM** (on-chip, shared memory) | ~20 MB суммарно | ~19 ТБ/с | супербыстрая, но крошечная; сюда грузят блоки во FlashAttention |
| **HBM / VRAM** | 80 GB | ~2 ТБ/с | основная память: веса, KV cache, активации |
| **CPU RAM / диск** | сотни GB+ | десятки GB/с | оффлоад (GGUF), медленно |

Разрыв в скорости SRAM vs HBM — почти **×10**. Поэтому «дёшево» — держать горячие данные в SRAM и минимизировать походы в HBM. Именно на этом построен FlashAttention.

### Flash Attention

- Стандартное вычисление внимания материализует матрицу `scores` размера `N × N` (`N` — длина последовательности) в медленной HBM → **квадратичная память** и много обращений к HBM.
- **FlashAttention** — алгоритм, ускоряющий внимание и на инференсе, и на обучении, **не создавая полную матрицу `N×N` в HBM**.
- Разбивает Q, K, V на **блоки (tiling)**, грузит их в быструю **SRAM** и считает внимание по блокам с «онлайн-softmax» (накапливает результат, не храня всю матрицу).
- Итог: **линейная память** по длине вместо квадратичной и кратно меньше обращений к HBM → ускорение и возможность длинного контекста.
- Требует аппаратной поддержки (**A100 и новее**); есть версии **v1 → v2 → v3** с растущей оптимизацией (v3 — под Hopper/H100).

> **Аналогия.** Вместо того чтобы разложить на столе (HBM) всю огромную таблицу перемножений и потом её читать, FlashAttention считает её по маленьким кусочкам в уме (SRAM), запоминая только промежуточный итог.

### Особенности работы KV cache

- Токены генерируются **итеративно** — до END-токена или лимита длины.
- Для каждого нового токена нужно выполнить весь набор вычислений.
- Чтобы не повторять расчёты, K и V для предыдущих токенов **кэшируют** (Q пересчитывается всегда).
- При большом контексте кэш достигает **десятков–сотен ГБ**, растут накладные расходы на перемещение данных между сегментами памяти.
- Память выделяется **заранее под максимальный контекст** и в процессе **сильно фрагментируется**.

### Paged Attention

Проблема классического KV cache: под каждый запрос память резервируется **непрерывным куском сразу под максимальный контекст** (например, 8192 токенов), даже если реально сгенерируется 200. Итог — до **60–80 % KV-памяти простаивает** (внутренняя + внешняя фрагментация).

**PagedAttention** (движок vLLM) решает это по образу **виртуальной памяти в ОС**:

- KV cache бьётся на небольшие **блоки (страницы)**, например по **16 токенов**.
- Память **аллоцируется поблочно по мере генерации** — не «про запас».
- Логически последовательный контекст запроса может лежать в **физически разрозненных блоках** (таблица блоков — как таблица страниц в ОС).
- Бонус: блоки можно **шарить** между запросами (общий системный промпт хранится один раз — это **prefix caching**).

Итог: потери памяти падают с 60–80 % до **< 4 %** → в ту же VRAM влезает в разы больше одновременных запросов.

> **Тезис блока:** PagedAttention — то, что позволяет держать **много параллельных запросов** без OOM и без раздувания VRAM «про запас». Это фундамент высокой пропускной способности vLLM.

### Батчинг: статический и динамический

Как показал roofline выше, decode **memory-bound** и GPU недозагружен. **Батчинг** объединяет запросы, чтобы веса читались из памяти один раз на весь батч, а ядра были заняты полезной работой.

| Тип батчинга | Как работает | Проблема |
|--------------|--------------|----------|
| **Без батчинга** | 1 запрос за раз | GPU почти простаивает (~5–10 % утилизации) |
| **Статический (наивный)** | Копим N запросов, обрабатываем батч целиком, ждём, пока **все** закончат | Короткие запросы **простаивают**, ожидая самый длинный; новые ждут конца батча |
| **Continuous (dynamic)** | Планировщик работает **после каждого токена**: закончившийся запрос сразу покидает батч, на его место **немедленно** входит новый | Максимальная утилизация; независимые prefill/decode |

**Пример (почему continuous лучше).** Статический батч из 4 запросов, которым нужно сгенерировать `50, 200, 60, 300` токенов:

- **Статический:** все ждут самый длинный (300 токенов). Запрос на 50 токенов закончил работу, но его слот **простаивает 250 шагов**. GPU недозагружен.
- **Continuous:** как только запрос на 50 токенов закончился, его слот **сразу занимает новый** запрос из очереди. Слоты всегда заполнены → пропускная способность выше в разы.

> **Тезис блока:** continuous (dynamic) батчинг — ключевой множитель пропускной способности. В связке с **PagedAttention** (память под блоки под каждый новый запрос) это и есть сердце **vLLM**. Именно поэтому в [ДЗ](../README.md) переход на vLLM даёт ~15–20× экономию GPU.

### Дополнительные техники: prefix caching, chunked prefill, speculative decoding

Помимо базовых, в современных движках есть ещё несколько важных приёмов (полезно знать для собеседований и тюнинга):

| Техника | Идея | Когда помогает |
|---------|------|----------------|
| **Prefix caching** | Кэшировать KV общего префикса (системный промпт, few-shot примеры) и переиспользовать между запросами | Одинаковый длинный системный промпт у всех запросов → экономия prefill |
| **Chunked prefill** | Резать длинный prefill на куски и **чередовать** с decode других запросов | Длинные промпты не «замораживают» генерацию у остальных (стабильный TTFT/TPOT) |
| **Speculative decoding** | Маленькая «черновая» модель предлагает несколько токенов, большая проверяет их **разом** | Ускорение decode в 2–3× без потери качества (проверка точная) |
| **KV cache quantization** | Хранить KV в FP8/INT8 вместо FP16 | Вдвое меньше KV cache → больше параллельных запросов / длиннее контекст |

### Параллелизм: tensor / pipeline

Большая модель (как 70B в FP16 = 140 GB) не влезает на одну карту — её **распределяют между GPU**:

| Вид параллелизма | Что делит | Особенности |
|------------------|-----------|-------------|
| **Tensor Parallelism (TP)** | Каждую матрицу весов «режет» между GPU (все карты работают над одним слоем одновременно) | Нужен быстрый интерконнект (**NVLink**); типично TP=2/4/8 внутри одного сервера |
| **Pipeline Parallelism (PP)** | Раздаёт **разные слои** на разные GPU (слои 1–20 на GPU-0, 21–40 на GPU-1…) | Экономит интерконнект, но появляется «пузырь» простоя между стадиями |

**Пример.** Llama-3-70B FP16 (~140 GB + overhead ≈ 168 GB) → **TP=4** на 4× A100-80GB (320 GB суммарно): веса делятся на 4, остаётся место под KV cache. Для 70B в INT4 (~42 GB) параллелизм ради памяти **не нужен** — модель влезает на одну A100-80GB.

> **Тезис блока:** параллелизм нужен, когда модель не помещается на карту (память) **или** когда одной карты не хватает по скорости. Для сайзинга: сначала считаем, сколько карт надо *по памяти*, потом — *по пропускной способности*, берём максимум.

### Несколько моделей на одном GPU: MIG и Time Slicing

Обратная задача: не все модели утилизируют целую карту (маленькая модель 7B в INT4 = ~4 GB на карте с 80 GB). Тогда GPU можно **делить** между несколькими моделями/задачами:

| Механизм | Суть | Изоляция | Ограничения |
|----------|------|:---:|-------------|
| **MIG** (Multi-Instance GPU) | **Физическое** разделение карты на изолированные профили с фиксированной памятью и ядрами | полная (аппаратная) | Только **A100 / H100 / B100**…; до **7** профилей на карту |
| **Time Slicing** | Разделение GPU между задачами **по времени** (чередование выполнения) | нет | Оверхед на переключение; конкуренция за память; альтернатива для карт **без MIG** (T4, L4, V100) |

**Пример MIG-профилей на A100-80GB.** Обозначение `Ng.Mgb` = `N` вычислительных «слайсов» и `M` GB памяти:

- `1g.10gb` × **7** — семь мелких инстансов (по ~10 GB) для лёгких моделей/сервисов;
- `2g.20gb` × 3, `3g.40gb` × 2 — средние;
- `7g.80gb` × 1 — вся карта целиком.

**Когда что:** одна большая модель под нагрузкой → берём **всю карту** (или TP на несколько). Много мелких моделей/тенантов с изоляцией (например, разным командам) → **MIG**. Нерегулярные dev/эксперименты без требований к изоляции → **Time Slicing**.

> **Тезис блока:** MIG — «нарезать один сервер на несколько мелких с гарантиями»; Time Slicing — «пустить несколько задач по очереди» без гарантий. Для прод-LLM под нагрузкой чаще нужна **вся карта или TP**, а не деление.

## Пошаговый пример сайзинга «с нуля»

Соберём всё вместе на упрощённой мини-задаче (полный расчёт под 1000 RPM — в [ДЗ](../README.md)).

**Дано:** нужно поднять **Llama-3-70B** для чат-бота, пик — **300 RPM**, средний ответ 200 токенов, средний контекст 1000 токенов. Бюджет ограничен.

**Шаг 1. Выбираем точность.** Чат-бот терпит небольшую потерю качества → берём **INT4 (AWQ)**. Веса: `70·10⁹ × 0.5 = 35 GB`.

**Шаг 2. Считаем VRAM на инстанс.** Веса + overhead (×1.2) = `35 × 1.2 ≈ 42 GB`. → влезает на **одну A100-80GB**, остаётся ~38 GB под KV cache.

**Шаг 3. Проверяем KV cache под нагрузку.** `KV/токен ≈ 0.3125 MB`. Одновременных запросов ≈ `RPS × latency = 5 × 8с ≈ 40`. KV = `40 × 1000 токенов × 0.3125 MB ≈ 12.5 GB` — влезает в оставшиеся 38 GB ✅.

**Шаг 4. Считаем пропускную способность.** Нужно `5 RPS × 200 токенов = 1000 output-токенов/с`. Одна A100-80GB с vLLM (INT4) даёт ~1800 токенов/с → **хватает одной карты** ✅ (с запасом).

**Шаг 5. Отказоустойчивость.** Для прода закладываем **N+1** → **2× A100-80GB** (вторая на случай отказа/обновления).

**Шаг 6. Движок и оптимизации.** **vLLM** (continuous batching + PagedAttention + FlashAttention). Без него понадобилось бы в ~15–20× больше карт.

**Итог:** 2× A100-80GB, Llama-3-70B INT4 (AWQ), vLLM. Дёшево, влезает по памяти, держит нагрузку с запасом.

## Итоги занятия

К концу занятия вы можете:

1. **Рассчитывать сайзинг** VRAM, необходимый для запуска LLM (`Параметры × Вес + KV cache + Overhead`).
2. Оптимизировать **обучение** LLM-моделей.
3. Оптимизировать **инференс** LLM-моделей (квантование, FlashAttention, PagedAttention, батчинг, MIG/Time Slicing).

**Практический вывод для архитектора:** сначала выбираем точность (FP16 vs INT4 — компромисс качество/память), затем движок инференса (**vLLM** с continuous batching + PagedAttention), затем считаем нужное число GPU под целевую пропускную способность (RPM) — см. расчёт в [ДЗ](../README.md).

## Глоссарий терминов и сокращений

| Термин | Расшифровка / значение |
|--------|------------------------|
| **VRAM** | Video RAM — видеопамять GPU, где лежат веса, активации и KV cache |
| **HBM** | High Bandwidth Memory — основная (большая, но относительно медленная) память GPU |
| **SRAM** | On-chip память GPU — маленькая, но очень быстрая (в неё грузят блоки во FlashAttention) |
| **Параметры (weights)** | Обучаемые веса модели; их число (например, 70B) определяет базовый объём памяти |
| **FP32 / FP16 / BF16** | Форматы чисел с плавающей точкой: 4 / 2 / 2 байта на элемент |
| **INT8 / INT4** | Целочисленные форматы квантования: 1 / 0.5 байта на параметр |
| **KV cache** | Кэш ключей (K) и значений (V) внимания для уже сгенерированных токенов |
| **GQA** | Grouped-Query Attention — общие K/V на группу голов; уменьшает KV cache (используется в Llama-3) |
| **MHA** | Multi-Head Attention — классическое многоголовое внимание (каждой голове свои K/V) |
| **Overhead** | Накладные расходы памяти: CUDA-контекст, активации, буферы, фрагментация |
| **Квантование** | Сжатие весов/активаций за счёт снижения точности представления |
| **PTQ / QAT** | Post-Training Quantization / Quantization Aware Training — после обучения / в процессе обучения |
| **Динамич./статич. квантование** | Калибровка активаций во время инференса / заранее на тестовых данных |
| **AWQ** | Activation-aware Weight Quantization — щадит наиболее влияющие «сверх-веса» |
| **GPTQ** | Послойная PTQ-квантизация с минимизацией ошибки через матрицу Гессиана |
| **GGUF** | Формат хранения + блочное квантование; запуск на слабом железе (в т.ч. CPU) |
| **Симметричное / асимметричное** | Квантование без / с zero-point (смещением нуля) |
| **FlashAttention** | Блочный алгоритм внимания, минимизирующий обращения к медленной памяти (A100+) |
| **PagedAttention** | Постраничное (блочное) управление KV cache; борется с фрагментацией (vLLM) |
| **Батчинг** | Объединение запросов в батч для параллельной обработки без лишних загрузок весов |
| **Continuous / dynamic batching** | Планирование батча после каждого токена; независимые prefill/decode |
| **prefill / decode** | Фаза обработки промпта / фаза пошаговой генерации токенов |
| **Memory-bound** | Операция, ограниченная пропускной способностью памяти, а не вычислениями |
| **MIG** | Multi-Instance GPU — аппаратное деление карты на изолированные профили (A100/H100+) |
| **Time Slicing** | Деление GPU между задачами по времени, без полной изоляции |
| **vLLM** | Высокопроизводительный движок инференса LLM (PagedAttention + continuous batching) |
| **RPM / RPS** | Requests per minute / per second — целевая нагрузка |
| **A100 / T4 / L4 / V100 / H100** | Модели GPU NVIDIA (80/16/24/32/80 ГБ VRAM соответственно) |
| **d / d_model (hidden size)** | Размерность скрытого состояния трансформера; параметры растут как `~d²` |
| **d_ff** | Внутренняя размерность FFN (обычно `≈ 4·d`) |
| **FFN** | Feed-Forward Network — полносвязный подблок слоя (основная доля параметров) |
| **SwiGLU** | Вариант FFN c 3 матрицами (в Llama); тяжелее классического FFN по параметрам |
| **RoPE** | Rotary Positional Embeddings — позиционное кодирование без обучаемых весов |
| **prefill / decode** | Фаза обработки промпта (compute-bound) / пошаговой генерации (memory-bound) |
| **TTFT** | Time To First Token — задержка до первого токена (определяется prefill) |
| **TPOT / ITL** | Time Per Output Token / Inter-Token Latency — время на каждый следующий токен (decode) |
| **GEMV / GEMM** | Умножение матрица×вектор (decode, memory-bound) / матрица×матрица (батч, compute-bound) |
| **Roofline** | Модель «потолка» производительности: упор в память (bandwidth) или в вычисления (FLOPS) |
| **Compute-bound / memory-bound** | Ограничение вычислениями / пропускной способностью памяти |
| **FP8 (E4M3 / E5M2)** | 8-битный формат с плавающей точкой (H100+); для KV cache и быстрого инференса |
| **scale / zero-point** | Коэффициент масштаба `s` и смещение нуля `z` в квантовании |
| **Per-tensor / per-channel / per-group** | Гранулярность подбора `s`/`z`: на матрицу / столбец / блок (обычно 128) |
| **Salient weights** | «Сверх-веса» (~1 %), сильнее всего влияющие на выход; их защищает AWQ |
| **Калибровка** | Прогон типичных данных для подбора диапазонов квантования (`s`, `z`) |
| **K-quant** | Семейство блочных квантований в GGUF (`Q4_K_M` и т.п.) |
| **Perplexity** | Метрика качества языковой модели (ниже — лучше); по ней оценивают потери от квантования |
| **Prefix caching** | Переиспользование KV общего префикса (системный промпт) между запросами |
| **Chunked prefill** | Разбиение длинного prefill на куски вперемешку с decode других запросов |
| **Speculative decoding** | Черновая мелкая модель предлагает токены, большая проверяет разом (ускорение 2–3×) |
| **Tensor Parallelism (TP)** | Разрезание каждой матрицы весов между GPU (нужен NVLink) |
| **Pipeline Parallelism (PP)** | Разные слои модели на разных GPU |
| **NVLink** | Быстрый интерконнект между GPU NVIDIA (нужен для эффективного TP) |
| **LoRA / QLoRA** | Дообучение через маленькие адаптеры / то же поверх 4-битной базы (экономия памяти) |
| **ZeRO / FSDP** | Шардирование весов, градиентов и состояний оптимизатора между GPU при обучении |
| **Gradient checkpointing** | Пересчёт активаций на backward вместо хранения (экономия памяти при обучении) |
| **Adam** | Оптимизатор; хранит 2 доп. состояния на параметр → память обучения ×~8 к весам |
| **OOM** | Out Of Memory — нехватка видеопамяти (падение процесса) |
