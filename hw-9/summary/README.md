# Раздел I. High-Load и Low-Latency инференс

## Что такое Highload

> **Highload** — комбинация НФТ к системе, при которых приходится применять сложные и компромиссные архитектурные решения в части **производительности, масштабируемости и отказоустойчивости**.

Ключевое слово — **компромиссные**: highload это не «сделать быстро», а осознанно чем-то заплатить (консистентностью, стоимостью, сложностью) за latency и пропускную способность.

**Три метрики, которые надо зафиксировать до проектирования:**

| Метрика | Что означает |
|---------|--------------|
| **RPS / TPS** | Пропускная способность: сколько запросов в секунду держим (среднее и пик) |
| **Latency (P95 / P99)** | Задержка ответа. Средняя бесполезна — считают перцентили |
| **Availability / SLO** | Доля успешных ответов в бюджете задержки |

---

## Шесть базовых паттернов highload

| Паттерн | Суть |
|---------|------|
| **Горизонтальное масштабирование / репликация** | Больше инстансов вместо более мощного железа |
| **Кэширование** | Не считать заново то, что уже считали |
| **Балансировка нагрузки** | Равномерное (или умное) распределение запросов по инстансам |
| **Шардирование и партиционирование** | Разделение данных/нагрузки по ключу |
| **Асинхронность и параллелизм** | Не блокировать клиента на время тяжёлой работы |
| **Геораспределённость и CDN** | Приблизить вычисления к пользователю |

---

## Специфика паттернов для AI

Все шесть паттернов работают и для AI, но ломаются в деталях.

### Балансировка нагрузки

- Инстансы моделей **не полностью stateless** (KV-кэш, загруженные веса, прогретые буферы).
- Нужно **батчевание** поступающих запросов — балансировщик должен помогать, а не мешать батчу.
- Запросы **сильно различаются по сложности** (10 токенов vs 8 000 токенов) — round-robin неадекватен.
- У LLM **принципиально разные требования у фаз Prefill и Decode**: prefill — compute-bound, decode — memory-bandwidth-bound. Отсюда идея их разделять (disaggregated serving).
- Часто нужны **специфичные балансировщики** или собственная реализация (routing по префиксу, по KV-кэшу, least-pending-requests).

### Автомасштабирование

- Старт нового инстанса модели **значительно дольше**, чем обычного сервиса (скачать веса → загрузить в VRAM → построить CUDA-графы).
- Модель после старта надо **прогревать**, иначе первые запросы очень медленные.
- **Редко бывает простаивающее GPU-оборудование** — «просто добавить нод» может быть физически невозможно.

> Вывод: реактивного автоскейлинга по факту нагрузки недостаточно — нужны тёплый резерв, предиктивное масштабирование и медленный scale-down.

### Кэширование

- **Сложно определить индекс кэша** так, чтобы hit rate был приемлемым (запросы на естественном языке почти никогда не совпадают побайтово).
- **Размер кэша больше традиционного** (ответы LLM, аудио, эмбеддинги).
- **Прогрев кэша нетривиален** или от него отказываются вовсе.
- **Специфичные виды кэша (KV-кэш)** требуют доставки в память GPU → глубокая интеграция с движком инференса и специальные инструменты.

---

## Semantic cache: что учитывать

**Semantic cache** — кэш, где ключ ищется не строгим совпадением строки, а **векторным поиском по смыслу** запроса.

Риски и ограничения (из занятия):

| Риск | Пояснение |
|------|-----------|
| **Накладные расходы на эмбеддер** | Каждый запрос надо векторизовать — это +время и +ресурсы даже при промахе |
| **Уникальные запросы** | Если все запросы разные, эффект **отрицательный**: платим за эмбеддер, не получая попаданий |
| **Сложный и долгий прогрев** | Кэш начинает работать не сразу |
| **Безопасность** | В ответах модели может быть персональная информация → нельзя отдавать её другому пользователю |
| **Нерелевантные ответы** | Ошибки семантического поиска = выдача пользователю неправильного ответа с высокой уверенностью |

---

## KV cache / prefix cache

**KV cache** — сохранение вычисленных Key/Value тензоров attention, чтобы не пересчитывать их для уже обработанных токенов.

- Используется **при генерации токенов в рамках одного запроса** (базовый механизм).
- Может использоваться **внешнее хранилище кэша** — тогда KV переиспользуется **между похожими запросами** (prefix cache).
- Даёт существенный прирост при **больших запросах с повторяющимся системным промптом и контекстом** — то есть ровно в RAG.
- Возможна **распределённая реализация** для нескольких инстансов (LMCache, Mooncake, vLLM Automatic Prefix Caching).

> Разница с semantic cache: semantic cache экономит **весь вызов LLM**, prefix cache экономит **фазу prefill** (то есть время до первого токена).

## Edge AI

**Edge computing** — вынос вычислений с центральных серверов на устройства/узлы рядом с пользователем.

| Плюсы | Минусы |
|-------|--------|
| Значительное снижение нагрузки на серверную инфраструктуру | Ограниченная вычислительная мощность edge-устройств |
| Меньшее время ответа пользователю | Качество генерации/предсказаний на edge ниже |
| Уменьшение сетевого трафика | Ограниченный выбор совместимых устройств |
| Проще и надёжнее работа с конфиденциальными данными (данные не уезжают) | Сложность доставки обновлений и дообучения |
| Автономность — работает без связи с сервером | Стоимость edge-устройств может превысить апгрейд серверов |

**Типовые сценарии:** умные колонки и голосовые ассистенты, автопилот и умный круиз-контроль, видеонаблюдение, IoT и умный дом, носимые медицинские устройства.

**Аппаратные платформы:** Nvidia Jetson (лидер), x86 (Intel/AMD), RockChip.

---

## Пример: потоковый синтез речи

**Требования:** синтез речи в потоке; минимальное время от запроса до **первого чанка аудио**; много однотипных запросов, но с разными параметрами голоса; неравномерная нагрузка с пиками.

**Проблемные места:**

1. Нарезка текста на фрагменты должна одновременно: быть пригодной для кэша, не терять семантику фраз, не превышать контекст модели синтеза.
2. Синтез всего аудио должен идти **на одном инстансе** модели (иначе стыки).
3. Максимальная оптимизация доставки эмбеддингов голосов в модель и прогрев их кэша.
4. Частота попадания в кэш аудио **очень зависит от алгоритма нарезки**.
5. Большой размер кэша синтезированного аудио.

> Общий урок: в AI-highload **выбор ключа кэширования — архитектурное решение**, а не деталь реализации. От него напрямую зависит и hit rate, и качество.

# Раздел II. Serverless vs Kubernetes

## Serverless (FaaS)

> **Serverless (FaaS)** — облачный подход, при котором разработчик пишет только код функции, а провайдер берёт на себя управление серверами, масштабирование и запуск. **Оплата — исключительно за время работы функции.**

**Основные шаги работы:** написать функцию → доставить в FaaS-среду (UI или автоматизированно) → определить триггер запуска → получить URL (если триггер — HTTP) → получить результат по URL или через другой триггер.

**Популярные решения:** AWS Lambda (пионер и лидер), Azure Functions, Google Cloud Functions, **Yandex Cloud Functions** (отечественное; **пока нет поддержки GPU**), **Knative** (on-prem, ставится в кластер K8s и даёт serverless на его базе), OpenFaaS, **KEDA**, Fission, KubeElasti.

**Knative на практике:** развернули hello-world → подов нет вообще; первое обращение → под создаётся; после периода неактивности → под завершается; при множестве запросов → автоматическое масштабирование числа подов.

---

## Плюсы и минусы Serverless

| Плюсы | Минусы |
|-------|--------|
| Не надо тратить время на инфраструктуру и её конфигурирование | **Время холодного старта** — может не подойти сервисам с малым временем ответа |
| Оплата только за время работы функции | Не подходит для долгих процессов (часто лимит ≤ 1 часа) |
| Автоматическое масштабирование силами провайдера | При активном использовании **дороже**, чем аренда сопоставимого железа |
| Отказоустойчивость обеспечивается провайдером | Плохо подходит для stateful-операций |
| | Vendor lock |

---

## Нюансы Serverless для ML

**Почему может подойти:** GPU дорог даже в аренде 24/7; утилизация GPU обычно очень низкая и хочется платить за использование, а не за простой; у многих задач инференса нет жёстких требований к времени ответа.

### 1. Холодный старт

- При первом обращении сервис может отвечать долго.
- ML-сервисы **загружают большие файлы моделей при старте** → старт ещё дольше.
- **Не использовать для сценариев, требующих мгновенного ответа.**
- Приёмы: регулярные короткие «пустые» вызовы для поддержания в памяти; опция провайдера «держать горячим» (стоит денег, не всегда рентабельно); запуск из **снэпшотов памяти** уже запущенного сервиса.

### 2. Время работы

- Лимит функции обычно 10–15 минут, максимум час; **таймаут API Gateway ещё ниже — 30–60 секунд**.
- Обработка запроса может занимать больше, чем позволяет HTTP-таймаут.
- **Решение:** асинхронная обработка — очереди + воркеры, callback / polling, результат в S3 или БД.

### 3. Хранение состояния

- Функции **не сохраняют состояние** между запусками.
- Managed DB для состояния; помнить про **исчерпание лимита соединений** при резком масштабировании (нужен pooler).
- **Redis** для состояния между вызовами разных функций; очереди — для оркестрации цепочек; иногда состояние можно отдавать клиенту.

### 4. Стоимость и безопасность

- Serverless выгоден при **низкой интенсивности** или **«рваном» профиле** нагрузки; при стабильно высокой нагрузке — в разы дороже аренды.
- Ставить **лимиты бюджета**, мониторить потребление; часто целесообразен **гибридный подход** (часть нагрузки FaaS, часть на классической инфраструктуре).
- Безопасность: интеграция с authn/authz провайдера, **отдельный сервисный аккаунт на функцию** с минимумом прав, сетевая изоляция через VPC.

---

## Матрица выбора: Serverless или Kubernetes

| Критерий | Serverless (FaaS / Knative) | Kubernetes |
|----------|------------------------------|------------|
| Профиль нагрузки | Рваный, редкий, непредсказуемый | Стабильно высокий |
| Требования к latency | Мягкие (секунды и выше) | Жёсткие (десятки–сотни мс) |
| Размер модели | Небольшая, быстро загружается | Большая, долгий прогрев |
| GPU | Часто недоступен (Yandex Cloud Functions — нет GPU) | Полный контроль, node pools, MIG |
| Состояние | Stateless | Можно stateful (KV-кэш, локальный RocksDB) |
| Стоимость при высокой нагрузке | Дороже | Дешевле |
| Кто отвечает за скейлинг | Провайдер | Вы: HPA / **KEDA** / Cluster Autoscaler |

> **Практический вывод:** для real-time инференса больших моделей под постоянной нагрузкой — **Kubernetes**. Serverless — для событийного «клея» вокруг: вебхуки, пост-обработка, нотификации, редкие batch-задачи. Гибрид — норма.

# Раздел III. EDA для AI

## Почему синхронность убивает масштабируемость

- **Связность:** в синхронной системе Producer обязан знать адрес и API Consumer'а.
- **Временная связность:** оба сервиса должны быть доступны одновременно.
- **Проблема для AI:** инференс тяжёлых моделей (BERT, LLM) занимает время. Блокировать клиентский запрос на 500 мс+ — дорого и рискованно.
- **Решение:** инверсия контроля через события.

---

## EDA: определение, плюсы, проблемы

> **Event-Driven Architecture (EDA)** — современный архитектурный шаблон, созданный из **несвязанных сервисов**, которые публикуют, потребляют или маршрутизируют **события**.

Микросервис, выполнивший действие, публикует событие в **брокер** — он называется **publisher** (продюсер). Другие сервисы, **consumer** (потребители), могут это событие обработать. EDA — **распределённая система**: компоненты на разных серверах, взаимодействие по сети.

| Преимущества | Проблемы |
|--------------|----------|
| **Слабая связанность** — продюсеры и консьюмеры не знают друг о друге, брокер посредник | **Понимание бизнес-процесса** — по коду одного сервиса не видно, как реализован процесс целиком |
| **Масштабирование** — продюсеры и консьюмеры масштабируются независимо | **Проектирование под отказ** — нужна **идемпотентность** (повторы) и **коммутативность** (сообщения не по порядку) |
| **Отказоустойчивость** — необработанное событие не подтверждается брокером, не теряется, будет переобработано другим инстансом | |

---

## Event vs Command vs Query

| Тип | Смысл | Ожидание реакции | Примеры |
|-----|-------|------------------|---------|
| **Событие (Event)** | «Факт» — сообщение о том, что состояние изменилось | Нет требования к другому сервису | `ProductAdded`, `OrderCreated` |
| **Команда (Command)** | «Глагол» — требование что-то сделать | Да, конкретный получатель отреагирует | `AddProduct`, `CreateOrder` |
| **Запрос (Query)** | Получение состояния объекта и возврат вызывающей стороне; **состояние не меняется** | Синхронный ответ | `getProduct`, `getOrder` (GET / SELECT) |

---

## Thin vs Fat Events

| | **Thin Event** | **Fat Event** |
|--|----------------|---------------|
| Содержимое | Только ID — получатель сам идёт в БД за данными | Изменённые данные (specific changes) или снимок всей записи (snapshot) |
| Плюс | Маленькое сообщение | **Автономность** консьюмера |
| Минус | **Нагрузка на БД** (каждый консьюмер делает запрос) | Размер сообщения |

**Форматы полезной нагрузки:** JSON, XML, Protobuf, Thrift, Avro.

> **Тезис занятия:** выбирайте **Fat Events**, чтобы снизить нагрузку на БД и повысить автономность сервисов. В highload-AI thin events особенно опасны: N консьюмеров × 10 000 событий/с = DDoS собственной базы.

---

## Pub/Sub и Dead Letter Queue

**Издатель-Подписчик (Pub/Sub):** один издатель — много подписчиков, издатель не знает, кто его слушает. Можно добавить новый AI-сервис (например, «анализ тональности»), не меняя код загрузчика файлов — просто подписаться на тот же топик.

**Отличие от Queue:** в очереди сообщение читает **один** консьюмер; в Pub/Sub копию получают **все активные подписчики**.

**Dead Letter Queue (DLQ):**

- **Проблема:** сообщение, которое крашит парсер или модель (битый PDF, атака на модель).
- **Риск:** без DLQ оно вечно крутится в цикле (infinite loop), забивая ресурсы.
- **Решение:** после N попыток изолируем сообщение в DLQ для ручного разбора.

---

## RabbitMQ vs Kafka

| Характеристика | **RabbitMQ** | **Kafka** |
|----------------|--------------|-----------|
| Модель | Очередь задач (**Smart Broker**) | Лог событий (**Dumb Broker**) |
| Доставка | Удаляется после прочтения (Ack) | Хранится N дней (**Replay**) |
| Сложность | Средняя | Высокая |
| Производительность | Средняя | Очень высокая |
| **AI Use Case** | **Inference Queue** — распределение задач на воркеры | **Training Data / Logs** — сбор данных для обучения |

---

## Идемпотентность и порядок событий

- Большинство брокеров по умолчанию дают **at-least-once**: если нет подтверждения об успешной обработке — событие отправляется повторно. → **Обработка должна быть идемпотентной** (дедупликация по `event_id`).
- Получить события **в правильном порядке** — отдельная работа (и сначала надо определить, что такое «правильный порядок»). Брокер должен знать **ключ партиционирования**, по которому определяется секция с поддержкой FIFO.

Пример: события `OrderCreated → ProductAdded → OrderCancelled` для агрегата `101` должны попасть в одну партицию — ключ партиционирования = ключ агрегата.

## Оркестрация vs Хореография

| | **Оркестрация (DAG)** | **Хореография (EDA)** |
|--|------------------------|------------------------|
| Кто управляет | Оркестратор сообщает участникам, какие локальные транзакции выполнять | Каждая локальная транзакция публикует доменные события, которые запускают транзакции в других сервисах |
| Плюс | Процесс виден в одном месте | Максимальная слабая связанность |
| Минус | Единая точка сложности/отказа | Процесс «размазан», трудно понять целиком |

Источник паттерна: [Saga на microservices.io](https://microservices.io/patterns/data/saga.html).

## Domain Events vs Data-Centric Events

> **Data-Centric Events** — паттерн, при котором под событиями подразумеваются события **изменения сущностей в БД** (`OrderCreated`, `OrderUpdated`).

> **Domain Events** — паттерн, при котором под событиями подразумеваются события **предметной области**, факты о том, что случилось (`OrderSubmitted`, `OrderProcessed`).

| | **Data-Centric (CRUD)** | **Domain Events** |
|--|--------------------------|-------------------|
| Что отражают | Физическое изменение данных (`UserUpdated`, `RowInserted`) | Свершившийся факт в терминах домена (`FraudScoreExceeded`, `AccountBlocked`) |
| Плюс | Просты в генерации — реализуются через **Change Data Capture** | Несут явную семантику и намерение |
| Минус | **Полная утрата бизнес-контекста**, консьюмер вынужден считать diff | Требуют аналитики и осознанного проектирования на стороне источника |

**Проектирование событий — с чего начинать:** от предметной области → с основного пользовательского сценария → каждое событие связывать с домейном → на первых итерациях не думать про реализацию на бэкенде. Однозначного ответа (`UserUpdated` / `UserBlocked` / `UserStatusChanged`?) не существует — как и для дизайна REST-интерфейса.

## Event Sourcing и CQRS

> **Event Sourcing** — паттерн, при котором в БД хранятся **только события**, а не состояние объекта.

| Плюсы | Минусы |
|-------|--------|
| Бесплатный аудит-лог | Тяжёлые миграции данных |
| Хорошая производительность event-store | Резкий рост объёмов → падение производительности (решается **снапшотами**) |
| **Темпоральные запросы** — состояние на любой момент времени | Сложные выборки (querying) — решается **CQRS** |
| Любая аналитика: хранятся все данные | |

> **CQRS (Command Query Responsibility Segregation)** — паттерн, при котором разделяются модели данных **для модификации и для чтения**.

Пример: `Transaction TABLE` (запись, поток событий) и отдельный `Balance TABLE` (проекция для чтения), наполняемый по событиям `InvoiceGenerated` / `InvoicePaid`.

### Хранение событий: Log Broker vs Event Store

| | **Log-based брокер (Kafka)** | **Event Store** |
|--|-------------------------------|-----------------|
| Назначение | Транспорт, буферизация, последовательное массовое чтение | БД для реализации Event Sourcing |
| Механика | Ограниченный retention, чтение по offsets | Независимые потоки (streams) по сущностям, оптимистичная блокировка |
| Ограничение / преимущество | Нет индексов → нельзя эффективно искать историю одного агрегата | Нативные проекции и чтение истории конкретного объекта |

**Стратегия интеграции:** Kafka — для высоконагруженной маршрутизации; Event Store — «золотой источник» (Source of Truth) для аудита и **Explainable AI (XAI)**.

## EDA и AI: фичи, обучение, топология инференса

### Real-time Feature Engineering

- **Проблема batch-подхода:** если считать агрегаты («число покупок за сутки») раз в ночь, модель не увидит атаку, начавшуюся 5 минут назад.
- **Решение — Streaming Aggregation:** вычисление фичей на лету оконными функциями, например `count(transactions) over (partition by user_id range interval '1 hour')`.
- **State Layer как feature store:** EDA позволяет наполнять Feature Store в реальном времени.
- **Главный риск — Training-Serving Skew:** логика расчёта фичей в стриминге (Java/Scala) отличается от аналитики (Python/Pandas).

### Реактивные паттерны обучения

| | Как | Проблема / плюс |
|--|-----|-----------------|
| **Static** | Cron: «переобучать каждое воскресенье» | Неэффективно, если данные не менялись; опасно, если появился новый тип мошенничества |
| **Dynamic** | Запуск пайплайна по **событию-триггеру** | Реагирует на реальность |

**Типы триггеров:** `DataDriftDetected` (распределение входов изменилось), `ConceptDriftDetected` (Accuracy/F1 на свежих данных упала ниже порога), `LabelsArrived` (накоплено N новых размеченных примеров).

**Асинхронная оценка:** ground truth часто отложен во времени (клиент оспорил транзакцию через 2 дня) — это тоже событие (`LabelDelayed`), которое должно попасть в Store.

### Топология Inference Pipeline

| Вариант | Как работает | Плюсы | Минусы |
|---------|--------------|-------|--------|
| **1. Embedded Model** (модель-библиотека) | Модель (ONNX, POJO) грузится прямо в память consumer-сервиса | Нулевой сетевой оверхед, максимальная пропускная способность | Не масштабируется отдельно от консьюмера, сложно обновлять (редеплой), конфликт ресурсов CPU/RAM |
| **2. External Model Service** (RPC / Sidecar) | Consumer получает событие, собирает фичи, делает gRPC/REST-запрос | Чёткое разделение ответственности, независимый скейлинг GPU-подов | Сетевые задержки, риск синхронной блокировки обработки очереди |
| **3. Asynchronous Inference** (Fully EDA) | Полностью через брокер | Максимальная развязка, буферизация пиков | Дополнительная задержка на запись/чтение брокера |

## Кейс: Fraud Monitoring (10 000 TPS, < 200 мс)

**Бизнес-цель:** блокировать подозрительные операции **до списания средств**.

**NFR:** latency строго **< 200 мс** на весь цикл (от запроса до ответа терминалу); при задержке валидации транзакция уходит на постобработку; **10 000 TPS** в пике.

**Constraints:** модель требует контекст — предрасчитанные агрегаты за 30 дней (средний чек, география). «Сырая» транзакция бесполезна без агрегатов.

### Анализ альтернатив

| Критерий | **A: Pure EDA (Async)** | **Б: Sidecar / Direct (Sync)** |
|----------|--------------------------|--------------------------------|
| Задержка | Две записи в Kafka и два чтения + время репликации | Данные через RAM (Unix Socket), колебания минимальны |
| Обработка ошибок | Модель упала → сообщение лежит в Kafka, нужен DLQ и разбор | Ошибка вызова → Flink сразу применяет Fallback («пропустить по лимитам») |
| Сложность разворачивания | Независимые сервисы: обновляем модель — Flink работает | Единый Pod: обновление модели требует рестарта Flink, сложный resource management |

### Архитектурные решения

| Требование | Проблема | Решение |
|------------|----------|---------|
| Строгий порядок событий | В распределённой системе порядок может быть нарушен | **`User_ID` как ключ партиционирования** |
| Latency < 200 мс | Ходить в PostgreSQL за историей на каждой транзакции — DDoS собственной базы | **Шардированные агрегаты хранятся прямо на диске/в памяти воркера** Stream Processor'а (локальный **RocksDB** на SSD), маршрутизация gRPC-трафика перед подами по шардам |
| Latency < 200 мс | Инфраструктура (Kafka/Flink) на JVM, а модели Data Scientists пишут на Python | Паттерн **sidecar**: Java и Python в одном Pod'е, общение через **gRPC over Unix Domain Socket** |

> Данные не покидают оперативную память сервера (loopback): скорость почти как у прямого вызова функции, но полная изоляция процессов.

## Semantic Cache (Azure Cosmos DB)

Источник: [learn.microsoft.com — Введение в семантический кэш](https://learn.microsoft.com/ru-ru/azure/cosmos-db/gen-ai/semantic-cache)

### Зачем

LLM имеют вычислительную стоимость, выражаемую в **токенах**. LLM **не сохраняют контекст** между запросами, поэтому с каждым запросом приходится передавать часть журнала чата — **контекстное окно** (скользящее окно запросов и ответов). Этот дополнительный текст увеличивает и стоимость, и задержку.

В паттерне **RAG** к промпту добавляются данные из внешнего источника — payload часто становится очень большим: тысячи токенов и несколько секунд ожидания. Обращение к LLM — обычно **самая дорогая услуга с самой высокой задержкой** в GenAI-приложении.

> **Semantic cache** — способ использовать предыдущие запросы пользователей и завершения LLM для ответа на **аналогичные** запросы через **поиск сходства векторов**.

### Как работает

| | Традиционный кэш | **Семантический кэш** |
|--|------------------|------------------------|
| Поиск | По ключам, совпадение строк | **Векторный запрос** к ключам, хранящимся как векторы |
| Результат | Обычно **один** результат | Может вернуть **несколько** результатов (это запрос, а не lookup) |

Текст преобразуется в **вектор внедрения (embedding)**, затем им ищутся наиболее **похожие** векторы в ключах кэша. Возможность дать пользователю несколько вариантов на выбор дополнительно снижает вычислительные затраты и позволяет держать кэш меньшего размера.

### Оценка сходства (similarity score)

- Диапазон **0 (нет сходства) — 1 (точное совпадение)**; показывает, насколько близки векторы в многомерном пространстве.
- Используется как **фильтр** (`WHERE`), ограничивающий результаты теми, что вероятнее совпадают с намерением пользователя.
- **Подбор порога — проба и ошибка:**
  - **слишком высокий** → кэш быстро заполняется несколькими ответами на похожие вопросы из-за постоянных промахов;
  - **слишком низкий** → кэш возвращает много неуместных ответов, не соответствующих намерению.

### Контекстное окно — критично

Чтобы кэш был эффективен, он **тоже должен учитывать контекст**: ключом должен быть не только текст последнего запроса, но и части запросов из журнала чата.

**Классический пример ошибки:**

1. Пользователь A: «Какое самое большое озеро в Северной Америке?» → «Озеро Верхнее». Кэшируем.
2. Пользователь A: «А какое второе по величине?» → с контекстом LLM отвечает «Озеро Гурон». Кэшируем **этот текст запроса**.
3. Пользователь B в другой сессии: «Какой самый большой стадион в Северной Америке?» → «Стадион Мичигана».
4. Пользователь B: «А какое второе по величине?» → кэш находит **точное совпадение** и возвращает **«Озеро Гурон»** — неверно.

**Реализация:** векторизовать **массив запросов из контекстного окна + последний запрос**, и этот вектор использовать в `WHERE` векторного запроса к ключу кэша. По мере скольжения окна любая последовательность запросов с высоким сходством отдаётся кэшем вместо генерации.

### Maintenance (обслуживание)

- Кэш может разрастись до огромного размера. Способы контроля: **TTL** для элементов, ограничение максимального размера, ограничение числа элементов.
- **Similarity score как рычаг экономии:** более низкий порог → больше попаданий → меньше генераций, но ценой менее релевантных результатов.
- **Гибрид TTL + счётчик попаданий:** хранить `hit_count` на элементе, инкрементировать patch-операцией и **переопределять TTL** для «горячих» элементов при достижении порога попаданий.
- **Кэш как источник аналитики:** содержимое кэша (как и журнал чата) даёт данные о поведении и тональности пользователей. Можно хранить всё, но показывать пользователям только свежее — дополнительным фильтром: `WHERE c.lastUpdated > @someDate ORDER BY c.lastUpdated DESC`.

## KEDA (Kubernetes Event-Driven Autoscaling)

Источник: [keda.sh](https://keda.sh/) · [Scaling Deployments](https://keda.sh/docs/latest/concepts/scaling-deployments/) · [ScaledObject spec](https://keda.sh/docs/latest/reference/scaledobject-spec/)

### Что это

> **KEDA** — event-driven автоскейлер для Kubernetes (CNCF Graduated project), который масштабирует любой ворклоад **по внешним метрикам** — длине очереди, лагу консьюмера, значению Prometheus-запроса и т.д., включая **scale-to-zero**.

**Как устроено:** KEDA мониторит источник событий и **отдаёт данные в стандартный HPA** — то есть не заменяет HPA, а расширяет его. Каждая реплика ворклоада активно вычитывает элементы из источника событий, сохраняя семантику брокера (порядок, retry, deadletter, checkpointing).

**Компоненты:** operator (контроллер, управляет масштабированием и 0↔1), metrics adapter (отдаёт метрики в HPA), admission webhooks (валидация ScaledObject), **scalers** — 70+ адаптеров (Kafka, RabbitMQ, Prometheus, SQS, Redis, Cron, PostgreSQL, …).

**Пример потока для Kafka:**

1. Нет сообщений → KEDA может масштабировать деплоймент **в ноль**.
2. Приходит сообщение → KEDA детектит событие и **активирует** деплоймент.
3. Под стартует, подключается к Kafka, начинает вычитывать сообщения.
4. Сообщений больше → KEDA передаёт метрику в HPA → **scale out**.

### Объекты

| Объект | Для чего |
|--------|----------|
| **ScaledObject** | Масштабирование Deployment / StatefulSet / любого Custom Resource (нужен подресурс `/scale`) |
| **ScaledJob** | Масштабирование через Kubernetes **Jobs** — для длительных задач |
| **TriggerAuthentication** | Отдельное описание доступа к источнику метрик (секреты, IRSA, Managed Identity) |

### Две фазы масштабирования

| Фаза | Кто решает | Диапазон | Параметр |
|------|-----------|----------|----------|
| **Activation** | KEDA operator (по функции `IsActive` скейлера) | **0 ↔ 1** | `activationThreshold` (опционален, по умолчанию 0) |
| **Scaling** | Штатный **HPA controller** по метрике от KEDA | **1 ↔ N** | `threshold` |

Важно:

- Активация происходит, когда значение **строго больше** порога (при `activationThreshold: 0` активация при значении ≥ 1).
- **Activation имеет приоритет над scaling:** при `threshold: 10` и `activationThreshold: 50` при 40 сообщениях ворклоад уедет в ноль, даже если HPA хотел 4 реплики.
- **Если `minReplicaCount >= 1`, скейлер всегда активен и `activation` игнорируется.**

### Полезные возможности

| Возможность | Суть |
|-------------|------|
| **`useCachedMetrics`** | HPA спрашивает метрику каждые ~15 с; кэширование значений в течение `pollingInterval` **существенно снижает нагрузку на скейлер**. Не поддерживается для `cpu`, `memory`, `cron` |
| **Pausing** | Аннотации `autoscaling.keda.sh/paused: "true"` (заморозить на текущем числе реплик) и `autoscaling.keda.sh/paused-replicas: "N"` (привести к N и заморозить) — для обслуживания кластера без удаления ресурса |
| **`scalingModifiers`** | Композиция нескольких триггеров формулой: `"(trig_one + trig_two)/2"`, тернарные операторы, `count([...],{#>1})`, вложенные условия. Формула возвращает **одно** число |
| **Transfer HPA ownership** | `scaledobject.keda.sh/transfer-hpa-ownership: "true"` — передать существующий HPA под управление ScaledObject |

### Long-running executions

Проблема: сообщение обрабатывается 3 часа, HPA решает уменьшить 4 реплики до 2 — **нельзя выбрать, какую реплику убить**, можно потерять задачу на 2.9-м часу.

Два способа:

1. **Container lifecycle:** не завершаться сразу по `SIGTERM`, а дообработать текущий батч; Kubernetes ждёт ответа или `terminationGracePeriodSeconds`. Также `preStop` hook. Минус: под всё это время в статусе `Terminating`.
2. **Run as jobs (`ScaledJob`):** выполнять event-driven код в Kubernetes Jobs вместо Deployment — задача живёт до завершения.

# Ключевые тезисы

1. **Highload — это про компромиссы.** Сначала фиксируем RPS, P95/P99 latency и SLO, потом выбираем, чем платим.
2. **Для AI ломаются все базовые паттерны:** инстансы не stateless, старт долгий, ключ кэша неочевиден, GPU дефицитен.
3. **Semantic cache — главный рычаг снижения нагрузки на LLM**, но: обязателен учёт **контекстного окна**, аккуратный подбор порога сходства, защита от утечки PII и мониторинг ложных попаданий.
4. **Prefix/KV cache и semantic cache решают разные задачи:** первый режет prefill (TTFT), второй убирает вызов LLM целиком.
5. **Serverless — для рваной нагрузки и мягкого latency;** для real-time инференса больших моделей — Kubernetes. Холодный старт ML-функции убивает SLO.
6. **EDA даёт независимое масштабирование продюсеров и консьюмеров** и сглаживает пики через буфер брокера.
7. **Fat Events** предпочтительнее thin: меньше нагрузки на БД, выше автономность.
8. **At-least-once по умолчанию** → идемпотентность обязательна; порядок обеспечивается ключом партиционирования.
9. **RabbitMQ — очередь инференса, Kafka — поток данных и логов** для обучения.
10. **Переобучение запускается по триггерам-событиям** (drift, новые метки), а не по cron.
11. **KEDA не заменяет HPA,** а кормит его внешними метриками; помнит про 0↔1 (activation) отдельно от 1↔N (scaling).
12. **Edge** снижает и latency, и нагрузку на бэкенд, но ограничен мощностью устройств и сложностью обновлений.

# Глоссарий

| Термин | Значение |
|--------|----------|
| **Highload** | Комбинация НФТ, требующая сложных компромиссных решений по производительности, масштабируемости и отказоустойчивости |
| **RPS / TPS** | Requests / Transactions per second — пропускная способность |
| **P95 / P99** | Перцентили задержки: 95%/99% запросов быстрее этого значения |
| **SLO** | Service Level Objective — целевой уровень (latency, доступность) |
| **TTFT** | Time To First Token — время до первого токена ответа LLM |
| **Prefill / Decode** | Фазы генерации LLM: обработка промпта (compute-bound) / выдача токенов (memory-bandwidth-bound) |
| **KV cache** | Кэш Key/Value тензоров attention, чтобы не пересчитывать уже обработанные токены |
| **Prefix cache** | Переиспользование KV-кэша общего префикса (системный промпт, контекст) между запросами |
| **Semantic cache** | Кэш с поиском ключа по векторному сходству смысла запроса, а не по совпадению строки |
| **Similarity score** | Оценка близости векторов от 0 (нет сходства) до 1 (точное совпадение) |
| **Контекстное окно** | Скользящее окно запросов и ответов, передаваемое LLM для сохранения контекста беседы |
| **Embedding** | Вектор внедрения — числовое представление текста |
| **ANN / HNSW** | Approximate Nearest Neighbor поиск / граф-индекс для него |
| **TTL** | Time To Live — срок жизни элемента кэша |
| **CDN** | Content Delivery Network — географически распределённая сеть кэширования |
| **Edge computing** | Вычисления на узлах/устройствах рядом с пользователем |
| **Geo-DNS** | DNS-маршрутизация клиента в ближайший/самый быстрый регион |
| **Serverless / FaaS** | Модель, где пишется только код функции, а инфраструктура и скейлинг — на провайдере; оплата за время работы |
| **Cold start** | Холодный старт — задержка первого запроса из-за поднятия инстанса и загрузки модели |
| **Knative** | On-prem serverless-платформа поверх Kubernetes |
| **KEDA** | Kubernetes Event-Driven Autoscaling — масштабирование по внешним метрикам, включая scale-to-zero |
| **ScaledObject / ScaledJob** | CRD KEDA для масштабирования Deployment/CR и Job соответственно |
| **HPA** | Horizontal Pod Autoscaler — штатный автоскейлер K8s, которого KEDA кормит метриками |
| **Activation vs Scaling** | Фаза 0↔1 (решает KEDA) и фаза 1↔N (решает HPA) |
| **EDA** | Event-Driven Architecture — архитектура из несвязанных сервисов, публикующих и потребляющих события |
| **Publisher / Consumer** | Продюсер события / потребитель события |
| **Event / Command / Query** | Факт о произошедшем / требование что-то сделать / чтение состояния без его изменения |
| **Thin / Fat Event** | Событие только с ID / событие с данными или снапшотом состояния |
| **Pub/Sub** | Один издатель — много подписчиков, копию получают все активные подписчики |
| **DLQ** | Dead Letter Queue — изоляция «отравленных» сообщений после N попыток |
| **At-least-once** | Гарантия доставки «хотя бы один раз» → возможны дубликаты |
| **Идемпотентность** | Повторная обработка того же события не меняет результат |
| **Коммутативность** | Корректная обработка сообщений, пришедших не по порядку |
| **Partition Key** | Ключ партиционирования, обеспечивающий FIFO внутри секции |
| **Оркестрация / Хореография** | Центральный оркестратор управляет шагами / сервисы реагируют на события друг друга |
| **Domain / Data-Centric Events** | События предметной области / события изменения строк в БД (CDC) |
| **CDC** | Change Data Capture — генерация событий из журнала изменений БД |
| **Event Sourcing** | В БД хранятся только события, а не состояние |
| **CQRS** | Разделение моделей данных для записи и для чтения |
| **Event Store** | БД для Event Sourcing: потоки по сущностям, проекции, оптимистичная блокировка |
| **Log Broker** | Брокер-лог (Kafka): retention, offsets, нет индексов по агрегату |
| **Streaming Aggregation** | Расчёт агрегатов на лету оконными функциями |
| **Feature Store** | Хранилище признаков, единое для обучения и инференса |
| **Training-Serving Skew** | Расхождение логики расчёта фичей между обучением и продом |
| **Data / Concept Drift** | Изменилось распределение входов X / изменилась связь X → Y |
| **XAI** | Explainable AI — объяснимость решений модели (аудит по событиям) |
| **Sidecar** | Дополнительный контейнер в том же Pod'е; связь через localhost / Unix socket |
| **Backpressure** | Обратное давление: сигнал источнику снизить темп при перегрузке |
| **Warm pool** | Тёплый резерв заранее прогретых инстансов модели |
